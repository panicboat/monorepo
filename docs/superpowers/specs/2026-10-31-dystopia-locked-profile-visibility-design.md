# Dystopia locked profile visibility design

## Context

#1809 の課題は、投稿の公開範囲とフォローの承認制を別々の設定にしたことで、鍵に何の効果があるのかが曖昧になったことである。
#1704（#1780）で鍵を一度「鍵マークを付けるだけ」の設定にし、役割は改めて決めることにした。
この設計書は、その役割を決める。

鍵の定義は次の 1 文である。

> 鍵をかけると、フォローしていない人から予定とクチコミが見えなくなる。

鍵が絞るのは、公開範囲が届かない情報（予定とクチコミ）である。
投稿の見え方は公開範囲が担当し続けるので、鍵と公開範囲は重ならない。

### Decisions by the user

- フォローしていない人に見えるのは、プロフィール情報と公開投稿まで。
- 鍵・承認制・公開範囲は別々の設定のまま残す。
  - 鍵付きで承認制がオフの状態も残す。
    - その場合は、誰でもフォローすれば予定とクチコミを見られる。
- 鍵付きのゲストが書いたクチコミは、本文と評価を見せて、書き手の名前を伏せる。
  - 両方の鍵を見て隠す案は、キャストの一覧が減り、全クチコミで計算する平均と合わなくなるので採らない。
  - キャストの鍵だけで決める案は、ゲストの名前が出続けるので採らない。
  - 一覧の持ち主の鍵で決める案は、鍵付きキャストのクチコミがゲスト側の一覧から見えてしまうので採らない。
- コメントと返信は対象外とし、#1867 で別に検討する。
- 規約とポリシーは、#1868 で機能改善に左右されない書き方に見直す。
  - #1868 を先に済ませ、この変更では本文を直さない。

### Decisions by the author of this spec

ユーザーに提示して異論がなかったものである。

- 対象のキャスト本人には、書き手の名前が見える。
  - カルテを書くなどの自己防衛に必要なため。
- 伏せたときの表示は「（非公開のゲスト）」にする。
  - 今の「（無効なゲスト）」は退会した人のように見えるため。
- 鍵付きキャストの平均評価は、クチコミと一緒にフォローしていない人から隠す。
- 鍵なしキャストの平均評価は、今のまま全クチコミで計算する。
- 個別のクチコミ画面も一覧と同じ見え方にする。
- 公開範囲を「全員」にした予定のお知らせ投稿は、今のまま見える。
  - 「公開投稿は見えてよい」の範囲に入るため。
- カルテに鍵は効かない。
  - ゲストが鍵だけでカルテを隠せると、キャストの自己防衛にならないため。
- 予定タブとクチコミタブは消さず、開くと「フォローすると見られます」と伝える。
- 鍵をかけても、すでに承認済みのフォロワーはそのまま見られる。

### Decisions made while writing this spec

ユーザーにはまだ提示していない。

- 鍵付きのキャストをフォローしていないゲストも、そのキャストのクチコミを書ける。
  - 書いた本人は自分のクチコミを今どおり見られる。
  - クチコミの作成は今もフォローを条件にしておらず、書く導線を鍵で閉じる理由が定義に含まれないため。
- 書き手の名前を伏せるときは、`author` だけでなく `author_profile_id` もレスポンスから消す。
  - ID が残ると、プロフィールを引いて書き手を特定できるため。
- フォロー中とフォロワーの一覧は、プロフィール情報の一部として扱い、鍵をかけても今のまま見せる。
- 鍵の判定はサーバーだけが持ち、画面はサーバーが返す「鍵で隠れている」の項目に従う。
  - 空の一覧だけでは「鍵で隠れている」と「0 件」を区別できないため。
  - 本人・承認待ち・別プロフィールなどの規則を画面側にも持つと、サーバーとずれるため。

## Goals

- 鍵の効果が 1 文で説明でき、サーバーの判定・画面・仕様書が同じ内容になっている。
- 規約とポリシーの本文が、鍵の動きと矛盾していない。
- 予定とクチコミの見え方を、API を直接呼んでも画面と同じに絞る（サーバーで判定する）。
- #1809 を閉じられる。

## Non-goals

- 規約とポリシーの見直し（#1868）。
- コメントと返信の見え方（#1867）。
- 承認制を鍵に統合すること。
- 投稿の公開範囲と、投稿画面の公開範囲の初期値を変えること。
- カルテの見え方を変えること。
- 検索とおすすめから鍵付きのプロフィールを外すこと。

## Anti-goals

- 鍵付きキャストの予定やクチコミが、フォローしていない人に、予定タブ・予定検索・クチコミ一覧・「書いたクチコミ」・最近のクチコミ・個別表示のどれか 1 つからでも見えること。
- 鍵付きゲストの名前や ID が、伏せるべき相手へのレスポンスに含まれること。
- 鍵付きキャストの平均評価や件数が、フォローしていない人へのレスポンスに含まれること。
- 伏せたクチコミが、退会した人のものに見えること。
- 承認待ちの人が、フォロワーとして扱われること。

## Rules

### Who passes a lock

閲覧者が次のどれかに当てはまると、そのプロフィールの鍵を通れる。

- プロフィールの鍵がオフ。
- 閲覧者が本人（使用中のプロフィールが同じ）。
- 閲覧者がそのプロフィールの承認済みフォロワー。

判定はプロフィール単位である。
同じアカウントの別プロフィールは、フォローしていなければ通れない（投稿の閲覧判定と同じ）。
判定は閲覧時に毎回行うので、鍵の切り替えはデータの移行なしにすぐ反映される。

### Schedules

| 場面 | 鍵を通れない閲覧者 |
|---|---|
| 予定タブ（一覧） | 空。<br>画面は「フォローすると見られます」と伝える |
| 予定検索 | 候補から外れる |
| お知らせ投稿 | 投稿の公開範囲に従う（変更なし） |

### Reviews

「キャストの鍵」は対象キャストの鍵、「ゲストの鍵」は書き手のゲストの鍵である。

| 場面 | 出る条件 | 書き手の名前 |
|---|---|---|
| 対象キャストのクチコミ一覧 | キャストの鍵を通れる | ゲストの鍵を通れるときだけ出す |
| ゲストの「書いたクチコミ」一覧 | ゲストの鍵を通れて、対象キャストが有効ならキャストの鍵も通れる | 出す |
| 最近のクチコミ（ホーム） | キャストの鍵を通れる | ゲストの鍵を通れるときだけ出す |
| 個別表示 | 上の一覧のどれかに出る | 出る一覧と同じ条件 |

既存の条件（有効性とブロック）には、この表の条件を足す。

例外は次の通りで、どれも既存の権限を維持する。

- 対象キャスト本人は、自分へのクチコミの一覧と個別表示を見られて、書き手の名前も見える。
- ゲスト本人は、自分の「書いたクチコミ」一覧をすべて見られる。
- 作者アカウント（`is_mine`）は、自分のクチコミ一覧と個別表示を見られて、書き手の名前も見える。
  - 同じアカウントの別プロフィールを使っているときも同じ。

書き手を伏せるときは、次のようにする。

- `author` と `author_profile_id` を返さない。
- 本文（評価・段階・結果・タグ・補足・日付）は返す。
- 書き手が有効でない場合は、今の「（無効なゲスト）」を優先する。

平均は次のようにする。

- キャストの鍵を通れない閲覧者には、平均評価・評価者数・件数を返さない（`NO_SUMMARY` と同じ）。
- 通れる閲覧者には、今と同じ全クチコミの値を返す。
  - 鍵付きゲストの評価も含む。
  - 閲覧者によって値は変わらない。

### Screens

- 予定タブとクチコミタブは、鍵を通れない閲覧者にも表示する。
  - 開くと、内容の代わりに「フォローすると見られます」と表示する。
  - 画面は自分で判定せず、サーバーが返す「鍵で隠れている」の項目に従う。
- 鍵付きキャストのクチコミタブでも、ゲストには「このキャストのクチコミを書く」を表示する。
- 伏せた書き手は「（非公開のゲスト）」と表示する。
  - 名前の押下でプロフィールへ移動しない。
- プロフィール編集画面の鍵のスイッチの説明を、この定義に合わせて書き直す。
  - スイッチをオンにすると承認制もオンになる動きは変えない。

## Changes

### Backend

- `dystopia/monolith/slices/schedule/use_cases/list_schedules.rb`: 鍵を通れない閲覧者には空を返す。
- `dystopia/monolith/slices/discovery/use_cases/search_schedules.rb`: `candidate_ids` で鍵を通れないキャストを除く。
  - ページングより前で除くので、ページの件数は崩れない。
- `dystopia/monolith/slices/review/use_cases/filter_visible_reviews.rb`: `call` と `recent` に鍵の条件を足す。
  - `readable?` は `call` を使うので、個別表示は自動で揃う。
- `dystopia/monolith/slices/review/use_cases/list_reviews_by_target.rb`: キャストの鍵を通れないときは、`NO_SUMMARY` を返す。
- `dystopia/monolith/slices/review/use_cases/present_reviews.rb`: 閲覧者に合わせて書き手を伏せる。
  - 今は `viewer_account_id` だけを受け取るので、`viewer_profile_id` も渡す。
- review の proto: 書き手を伏せたことを画面に伝える項目を足す。
  - 「（無効なゲスト）」と「（非公開のゲスト）」を、`author` の有無だけでは区別できないため。
- review と schedule の proto: 対象キャストのクチコミ一覧、「書いたクチコミ」一覧、予定の一覧のレスポンスに、鍵で隠れていることを伝える項目を足す。
- `follow_repo.status_batch` が承認済みの判定に使える。
  - 鍵の判定を複数の slice に書かず、1 か所にまとめる。

### Frontend

- `dystopia/frontend/src/modules/schedule/components/ScheduleTab.tsx` と `dystopia/frontend/src/modules/review/components/CastReviewsTab.tsx`、`AuthorReviewsTab.tsx`: 鍵を通れない閲覧者への表示を足す。
- `dystopia/frontend/src/components/ui/profile-name.tsx`: 「（非公開のゲスト）」の定数を足す。
- `dystopia/frontend/src/modules/review/components/ReviewCard.tsx` と `dystopia/frontend/src/modules/review/lib/mappers.ts`: 伏せた書き手を表示する。
- `dystopia/frontend/src/modules/profile/components/EditProfileSheet.tsx`: スイッチの説明を直す。

### Docs

`dystopia/docs` の次の仕様書を、新しい動きに書き直す。

- `features/profiles.md`: 鍵とフォローの承認制の節。
- `features/follows-and-blocks.md`: 鍵は閲覧にもフォローにも効かないとしている箇所と、その理由。
- `features/reviews.md`: 閲覧の表、平均、鍵は条件にならないとしている箇所。
- `features/schedules.md`: 予定の見え方の表と冒頭の文。
- `features/search.md`: 予定検索の条件の表。
- `data-model.md`: `is_private` の説明（今は「鍵マークを付けるか」）。

`features/posts.md` の、鍵は投稿の閲覧可否に関係しないとしている箇所は、今も正しいので変えない。

### Legal

規約とポリシーの本文は、この変更では直さない。

- #1868 が merge されるまで、この変更は merge しない。
  - 今の本文には「鍵をかけても、プロフィールの情報と投稿が誰に表示されるかは変わりません」などの言い切りがあり、先に出すと実装と食い違うため。
- 実装の着手前に、#1868 の後の本文と、この設計書の Rules が食い違わないことを確かめる。
  - 食い違う文が残っていたら、機能の内容を本文に足さず、#1868 の方針に沿って直す。

## Testing

- 鍵の組み合わせ 4 通り × 閲覧者（本人、対象キャスト本人、作者アカウント、両方のフォロワー、片方のフォロワー、承認待ち、フォローなし）を、クチコミの一覧・最近・個別表示で確かめる。
  - 名前を伏せたレスポンスに `author` と `author_profile_id` が含まれないことを確かめる。
- 鍵付きキャストの平均が、鍵を通れない閲覧者に 0 で返り、通れる閲覧者には鍵付きゲストの評価を含んで返ることを確かめる。
- 予定タブと予定検索を、同じ閲覧者の種類で確かめる。
- 予定検索で、除外があってもページングが崩れないことを確かめる。
- 鍵のオン・オフで、データを変えずに見え方が切り替わることを確かめる。
- 鍵付きで承認制がオフの場合に、フォロー直後から見えることを確かめる。
- 画面: 2 つのタブの案内の表示、「（非公開のゲスト）」の表示、鍵付きキャストのクチコミを書くボタンの表示を vitest で確かめる。
- monolith の CI は rspec を回さないので、ローカルで rspec を実行して判定する。
- 実機で、鍵付きキャストとフォローしていないゲストの組み合わせを 1 通り確かめる。
