# Dystopia karte experience design

## Purpose

キャストがゲストの予約・接客に関する全体像を短時間で確認し、必要な場合に個別の出来事を読める体験を提供する。記録は予約・接客・接客後を通じて一つのカルテに蓄積し、対応結果を中心に少ない操作で入力する。

サイト全体の配置・配色・動きは [参照HTML](https://github.com/user-attachments/files/33307359/dystopia_city_motion_ux_v2.html) に合わせる。各操作はバックエンドの実データへ接続し、カルテの仕様にAPI・データモデル・画面をそろえる。

## Scope

- 共通の配色・入力部品・ボタン・タブ・シェル、ホーム、検索、通知、メッセージ、足跡、ブックマーク、ランキング、プロフィール、設定、自分のカルテ・レビューに参照HTMLの表示規則を適用する。
- 投稿、レビュー、プロフィールの作成・編集、詳細表示を右側パネルへ接続する。画像・動画、SNS項目、公開範囲、フォロー・ブロック、未読表示などの既存操作を実データで扱う。
- カルテの出来事、星評価、ライフサイクル、集計、共有フィード、自分の一覧、ゲストプロフィールからの閲覧を実装する。
- 出勤予定は複数日を選択して同じ時間帯を適用できるようにする。

課金プラン、ゲスト本人へのカルテ表示、変更履歴・監査ログ、専用の通報・訂正・削除申請、AI分析、ランキング・評価による利用制限は追加しない。既存の通報処理は引き続き利用できる。

## UI architecture

### Shell and styling

既存のNext.jsルート、認証、操作中プロフィール、SWRキャッシュの境界を使用する。参照HTMLのダミーデータや直接DOMを書き換えるスクリプトは製品へ持ち込まない。セマンティックなCSSトークンと既存の共有部品を更新するため、ライト・ダーク・システムのテーマ選択が各画面へ適用される。

PCはサイドナビ・中央の内容・おすすめの構成とし、狭い幅ではおすすめ、さらに狭い幅ではサイドナビを非表示にする。既存の `md`・`xl` にレイアウトを合わせ、モバイルのヘッダー、下部ナビ、安全領域、メッセージ入力欄が重ならないことを検証する。

`ComposeLauncher` と `FlowerMenu` のタップ・スライド・キーボード操作を維持する。投稿・メッセージ・カルテまたはレビューの選択は、既存のロールと宛先選択へ接続する。PCの作成ボタンは複数の作成操作を選べることが分かる文言にする。

### Side panels and motion

共有の `SideSheet` を既存の `@radix-ui/react-dialog` に基づいて構成する。タイトル、戻る操作、閉じる操作、スクロールする本文、必要な画面だけで使用する操作フッターを持つ。モバイルは全幅、PCは参照HTMLの幅で表示する。同時に開く操作パネルは一つとする。

作成・編集・詳細は右からスライドし、ルート・タブ・パネル内の段階切り替えは控えめにフェードする。開閉のCSSアニメーションはRadixのマウント管理に合わせる。[Radixの説明](https://www.radix-ui.com/primitives/docs/guides/animation) に従い、終了アニメーションの途中で呼び出し側がパネルを破棄しない。

フォーカスはパネル内に留まり、閉じたときは起点へ戻る。Esc、閉じるボタン、背景、ブラウザの戻るで閉じられる。宛先や記入画面から一つ前の段階へ戻る操作はパネル内で行う。[Dialogのアクセシビリティ](https://www.radix-ui.com/primitives/docs/components/dialog) を引き継ぐ。

ルート変更のフェードはページやメッセージのプロバイダーを再マウントせずに適用する。プロフィール切り替えは既存のキャッシュ分離を維持し、前のプロフィールのパネルや取得結果を次のプロフィールに表示しない。`prefers-reduced-motion` ではスライドとフェードを停止する。

投稿詳細とメッセージスレッドの既存URLは引き続き直接開ける。一覧からの詳細表示には右側パネルを使い、URLへの直接アクセスではその詳細の内容をページとして表示する。投稿への返信、メッセージ送信、メディア表示はそれぞれの既存処理を使用する。

## Karte experience

### Entry points

| 入口 | 優先表示・操作 |
|---|---|
| ホームのカルテタブ | 新着の記録者、対象ゲスト、星評価または未評価、状態、最後に追加した出来事。カードから詳細を開く |
| メニューの自分のカルテ | 自分の件数、記録中・完了の件数、全件・記録中・完了の絞り込み、新規作成 |
| ゲストプロフィールのカルテタブ | 平均評価、評価したキャスト数、集計対象カルテ数、そのゲストの個別カルテ |
| フラワータッチのカルテ | 既存の `RecipientPicker` でゲストを選択して記入画面を開く |
| ゲストプロフィールの作成操作 | 対象ゲストを引き継いで記入画面を開く |

ホームには記録中と完了の両方を、作成直後から掲載する。新着一覧は作成日時の降順とし、同じ日時はIDで順序を確定する。追記・編集で新着の先頭へ移動させないため、ページング中に同じカルテを繰り返し表示しない。

自分の一覧はアカウント単位で取得する。記録者は作成時のプロフィールのままとし、別プロフィールから操作しても書き換えない。操作中と異なるプロフィールで記録したカルテには、既存の記録者注記を表示する。

### Recording

一つのカルテは一回の予約・接客のまとまりとする。予約、接客、接客後のどの段階からでも作成でき、同じ段階に複数の出来事を追加できる。次回の利用は新しいカルテとして作成する。

1. 対象ゲストを選択する。プロフィールから開始した場合はそのゲストを使用する。
2. 段階、対応結果、発生日を指定する。
3. 必要に応じて複数の詳細タグ、補足、カルテ全体の星評価を入力する。
4. 保存成功後、記録中のカルテとして表示し、関連する一覧と集計を再取得する。

対応結果と詳細タグは [カルテの概要設計](https://github.com/panicboat/monorepo/issues/1519) の各段階の候補を採用する。APIは段階・結果・タグの安定した識別子を扱い、画面に日本語のラベルを表示する。段階に属さない結果やタグはサーバーで拒否する。

初期段階は予約、対応結果は未選択、発生日は日本の日付で当日とする。発生日は実在する日付を必須とし、日付だけの値として保存する。段階変更では対応結果とタグを選び直し、発生日と補足は保持する。

補足は出来事ごとに500文字までとする。「無断キャンセル・来店なし」「途中終了」「トラブル発生」、支払いトラブルまたは合意条件に反する要求を示すタグを選択した出来事では、空白以外の補足を必須とする。星1のカルテも、少なくとも一つの出来事か既存メモに補足が必要とする。作成・内容変更・完了時に保存後の内容全体を検証し、出来事の編集・削除でこの条件を崩さない。それ以外は対応結果だけで記録できる。

星評価はカルテ全体に一つで、初期値は未評価とする。1〜5の整数を選択でき、「未評価にする」で解除できる。3が標準であることと、評価対象が予約・接客の信頼性であることを入力画面に表示する。

### Details and lifecycle

詳細には対象ゲスト、記録者、星評価、状態、作成・更新日時を表示する。出来事を予約・接客・接客後の段階別に並べ、各段階では発生日、記録日時、IDの順で順序を確定する。過去日の出来事を後から追加しても、発生日に対応した位置に表示する。

| 状態・操作 | 動作 |
|---|---|
| 新規保存 | 記録中として保存する |
| 記録中 | 所有者が出来事の追記・編集・削除、星評価の変更、カルテの削除を行える |
| 完了する | 明示操作で完了する。評価があれば集計へ加える |
| 完了 | 全キャストが閲覧できる。内容・星評価の変更と出来事の追加・削除は拒否する |
| 再オープン | 所有者が記録中へ戻す。記録と評価を保持し、集計から一時的に除外する |
| 再完了 | 最新の評価で集計へ戻す |
| カルテを削除 | 所有者が確認後に削除する。状態にかかわらず集計から除外する |

完了と再オープンは同じ画面で状態を更新する。同じ状態への操作は成功として現在の記録を返し、日時を変更しない。最後の出来事を削除して空のカルテにはできない。

## Data and permissions

### Storage

既存の `karte.entries` をカルテの親として拡張し、出来事を `karte.events` に保存する。親は所有アカウント、記録者プロフィール、対象ゲスト、任意の評価、状態、完了日時を持つ。出来事は親ID、段階、対応結果、詳細タグ、補足、発生日、作成・更新日時を持つ。

子テーブル方式は出来事単位で更新でき、履歴配列全体の上書きで他の追記を失うことを避けられる。JSONにまとめる方式と比べて取得処理は増えるため、一覧で表示する最後の出来事と件数、詳細で表示する全出来事を区別し、一覧の件数分だけ出来事を再取得する構成にはしない。

作成は親と最初の出来事を一つのトランザクションで保存する。内容・出来事・状態の変更は親をロックした同じトランザクションで所有権と状態を検証する。完了と追記が競合しても、完了した記録への変更を確定しない。親の削除では子の出来事も削除する。

### Access

既存の認証と `AuthorizeCastAccess` を使用し、閲覧・作成はキャスト全体に提供する。店舗の制限は設けない。料金・課金条件の変更は対象に含めない。

編集・追記・削除・完了・再オープンは所有アカウントだけが行える。同一アカウントの別プロフィールからも操作できる。他キャストは閲覧だけを行え、ゲストはAPIへ直接アクセスしてもカルテを取得・操作できない。

所有アカウントIDはクライアントへ公開しない。既存の `isMine` と記録者プロフィールを返し、複数プロフィールの内部的な紐付きを表示しない。削除したプロフィールの記録を残す既存方針も維持する。

### Migration

既存のカルテ、評価、メモ、識別子、記録者、対象、日時、通報情報を保持する。既存行は完了済みにし、評価の列を未評価も保存できるようにする。新規の親は記録中とする。

既存メモには発生日・段階・対応結果がないため、出来事を捏造せず「過去のメモ」として詳細に表示する。記録日時を発生日へ読み替えない。既存形式の記録は出来事が空でも閲覧・再オープンでき、再オープン後にメモ編集と出来事の追加を行える。移行済みの完了記録には入力条件を遡って適用せず、内容変更や再完了で補足必須条件を検証する。

既存行の評価は完了済みカルテとして集計する。集計方式をアカウント単位へ変更するため、同じアカウントが多数記録したゲストの平均値は、既存の単純平均と異なる場合がある。

## Aggregation

対象ゲストの完了済み・評価ありの親だけを集計する。各所有アカウントの平均を計算した後、その平均を同じ重みで平均する。出来事の件数や記録したプロフィールの数は重みにしない。

例えば一人が星5のカルテを3件、もう一人が星1を1件持つ場合、総合平均は3.0、評価者数は2人、集計対象は4件となる。同一アカウントの別プロフィールによる記録も同じ評価者として扱う。

集計はサーバーで行い、一覧のページングとは独立した値を返す。画面は小数第1位で表示する。集計対象が0件なら「未評価」と表示し、カルテが0件の場合と区別する。完了・再オープン・評価変更・削除後は再取得した集計を表示する。

## API contracts

既存のRPC名と既存フィールド番号を維持し、状態・出来事・件数を追加する。RubyとTypeScriptの生成コード、BFFの変換、フロントエンドの型・フックを同じ契約にそろえる。既存の投稿・メッセージ・プロフィール・レビュー等のリクエスト項目を、参照HTMLの少ない入力項目に合わせて削らない。

| HTTP操作 | バックエンドの役割 |
|---|---|
| `POST /api/karte` | `CreateEntry` が対象ゲスト、任意の評価、必須の最初の出来事を受け取り、親と出来事を保存する |
| `GET /api/karte/[id]` | `GetEntry` が所有権の表示情報と全出来事を返す |
| `PATCH /api/karte/[id]` | `UpdateEntry` が記録中の星評価と既存メモを変更する |
| `DELETE /api/karte/[id]` | `DeleteEntry` が所有者のカルテを削除する |
| `POST /api/karte/[id]/events` | `AddEvent` が記録中のカルテへ出来事を追加する |
| `PATCH /api/karte/[id]/events/[eventId]` | `UpdateEvent` が所属する出来事を変更する |
| `DELETE /api/karte/[id]/events/[eventId]` | `DeleteEvent` が所属する出来事を削除する |
| `POST /api/karte/[id]/close` | `CloseEntry` が完了させる |
| `POST /api/karte/[id]/reopen` | `ReopenEntry` が記録中へ戻す |

新規作成では最初の出来事を必須とし、星評価と自由メモだけの作成フォームを新規形式へ接続し直す。既存の対象別・自分・新着一覧のエンドポイントは、状態、最後に追加した出来事、出来事件数を返す。対象別一覧は平均・評価者数・集計対象数を返し、自分の一覧は状態の絞り込みと全体の状態別件数を扱う。

星評価の更新では、JSONの省略を未変更、`null` を未評価、1〜5を設定値として区別する。protobufはpresenceを持つ評価フィールドを使用し、未指定を未変更、明示した0を未評価への変更として扱う。レスポンスと画面の型では未評価を `null` とし、0点の評価として表示しない。

BFFとバックエンドで必須項目、日付、評価範囲、文字数、段階と結果・タグの対応を検証する。認証失敗は401、権限違反は403、対象が存在しない場合は404、完了状態との競合は409、入力不備は400として画面へ伝える。存在しない出来事や別のカルテの出来事IDで更新・削除しない。

## Other connected flows

| 画面・操作 | 接続と完了条件 |
|---|---|
| 投稿作成・編集・返信 | 既存の本文、添付、公開範囲、送信処理を使用し、保存後の再取得で表示を確認する |
| メッセージ | 既存の宛先候補と送信条件を使用し、スレッド開始・送信後に保存した内容を表示する |
| レビュー | 既存の評価・本文・表示設定・所有権へ接続し、保存・編集・削除後に再取得する |
| プロフィール | 既存の画像、基本情報、身体情報、SNS、公開設定、人格の管理・切り替えへ接続する |
| 検索・通知・足跡等 | 各一覧・絞り込み・未読・フォロー等を既存の取得・変更処理へ接続する |
| 出勤の複数日編集 | 2週間の表示内で日を選び、既存の `useSaveSchedule` または `useDeleteSchedule` を日ごとに実行する |

出勤の保存は呼び出し側が全件の完了を待つ。成功した日を再取得し、失敗した日を選択したままエラーと再試行を表示する。全件が成功する前に成功として閉じず、すでに成功した日の結果を巻き戻したように表示しない。「休み」は既存の削除処理を使用し、未設定と区別する永続状態は追加しない。

## Errors and resource ownership

API処理中は対象操作の二重送信を防ぐ。保存が失敗したときは入力を保持し、フォーム内にエラーを表示する。成功時だけ成功通知と再取得を実行する。詳細・一覧の取得失敗には再試行を表示し、権限エラーを空一覧として扱わない。

新しいポーリングや常駐処理は追加しない。リクエストを開始したフック・フォームが完了を待ち、取得結果を終了した画面や異なるプロフィールへ適用しない。保存エラーはフォームへ返し、保存中に画面が破棄された場合は既存のトーストへ返す。アニメーションはコンポーネントの破棄時に停止する。既存のメッセージ取得処理は、そのプロバイダーが引き続き管理する。

参照HTMLに含まれる「デモ」「モック」「MVPの内部実装」などの説明は製品に表示しない。入力条件、評価の意味、共有範囲、保存結果など、操作の判断に必要な情報を表示する。

## Verification

### Backend and contracts

- 一つのカルテへ同じ段階と別の段階を追記でき、過去日の記録も保存できる。
- 段階に属さない結果・タグ、不正な日付、範囲外評価、補足必須条件を満たさない入力が拒否される。
- ゲストと他のアカウントによる変更が拒否され、同じアカウントの別プロフィールからの操作は許可される。
- 完了・再オープン・削除と集計が一致し、未評価は集計されない。複数プロフィールが別の評価者として数えられない。
- 完了と追記が競合しても完了後の内容変更を確定しない。
- 既存行の評価・メモ・ID・通報情報が移行で保持され、発生日が捏造されない。
- gRPCとBFFを通して評価の省略・解除・設定、出来事、状態、所有権の表示を確認する。

### Frontend behavior

- 作成、追記、出来事編集・削除、評価解除、完了、再オープン、カルテ削除が再取得した実データと一致する。
- ホーム、自分、ゲストプロフィールの表示目的と件数・平均が一致する。
- 星1などの補足必須条件、段階変更、発生日、エラー後の入力保持を確認する。
- パネルの開閉、段階の戻る操作、フォーカス、Esc、ブラウザの戻る、動き軽減を確認する。
- フラワータッチのタップ・スライドとキーボード操作、プロフィール切り替え後のキャッシュ分離を確認する。
- 複数日の出勤編集で一部のAPIが失敗した場合に、保存した日と再試行する日を区別できる。
- 既存の投稿・メッセージ・レビュー・プロフィール・設定のリクエストと操作の回帰を確認する。

### Connected acceptance

1. 型検査、変更箇所のlint、関連するVitest・RSpecを実行し、失敗を解消する。
2. ローカルのバックエンドとフロントエンドを接続し、キャストとゲストで主要操作を実行する。
3. モバイル・タブレット・PCの幅でダーク・ライト、長い本文、パネル内スクロール、メディア、入力欄の配置を確認する。
4. 保存後にページを再取得して、永続化した記録と集計を確認する。これらが一致した時点で連携の受け入れ条件を満たす。
